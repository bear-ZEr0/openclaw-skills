# 阶段12: 挑战模式 (Challenge Mode)

## 阶段目标
AI自我挑战，发现设计遗漏的问题。

## AI角色
**批判性思考者** - 主动寻找设计漏洞

## 挑战类型

### 类型1: 边界场景
探索极端情况下的系统行为。

### 类型2: 异常流
考虑错误和失败情况。

### 类型3: 用户体验
从用户角度发现体验问题。

### 类型4: 性能与安全
考虑非功能性问题。

## 示例

```markdown
## 挑战模式报告: 番茄钟App

### 挑战1: 边界场景 - 进程被杀

**挑战问题**:
"如果用户在使用中强行杀进程，数据会不会丢失？计时还会继续吗？"

**发现的问题**:
当前设计没有考虑App被系统杀死后恢复的状态。如果用户杀了App，再打开时：
1. 正在进行的番茄钟状态丢失
2. 用户不知道之前专注了多久
3. 统计数据不完整

**影响分析**:
- 影响范围: 所有用户，特别是内存小的手机
- 严重程度: 高
- 发生概率: 中（用户主动杀进程的概率不高，但系统杀后台很常见）

**解决方案**:
1. 每10秒保存一次当前计时状态到本地
2. App启动时检查是否有未完成的计时
3. 如果有，询问用户是继续还是放弃
4. 在通知栏显示持续计时，减少被杀概率

**需要在PRD中更新**:
- [ ] F-001 增加"状态恢复"要求
- [ ] 新增功能"启动时检查未完成计时"

### 挑战2: 异常流 - 时间设置错误

**挑战问题**:
"如果用户把系统时间往后调，会发生什么？可以作弊完成番茄钟吗？"

**发现的问题**:
如果用户将手机时间往后调1小时，App会误判番茄钟已完成。

**影响分析**:
- 影响范围: 想作弊的用户
- 严重程度: 中
- 发生概率: 低

**解决方案**:
1. 使用系统elapsedRealtime()而不是wall clock time
2. 记录实际经过的毫秒数，不受系统时间影响
3. 或者：记录开始时间戳，每次检查用当前时间-开始时间

**需要在PRD中更新**:
- [ ] F-001 技术要求：使用elapsedRealtime()

### 挑战3: 用户体验 - 忘记停止

**挑战问题**:
"如果用户开始番茄钟后忘了停止，App会一直计时吗？计到哪一天？"

**发现的问题**:
没有最大计时限制，可能导致：
1. 用户忘了停止，计时跑了几天
2. 统计数据异常（一个番茄钟几十小时）
3. 电池持续消耗

**影响分析**:
- 影响范围: 偶尔发生的用户
- 严重程度: 中
- 发生概率: 中

**解决方案**:
1. 设置最大计时限制（如2小时）
2. 超过限制自动停止并提示用户
3. 或者：检测长时间无交互，询问是否继续

**需要在PRD中更新**:
- [ ] F-001 增加最大计时限制要求

### 挑战4: 性能 - 数据累积

**挑战问题**:
"如果用户每天使用10次，一年后数据量有多大？会影响性能吗？"

**发现的问题**:
一年3650条记录，如果不做归档/清理，可能导致：
1. 查询变慢
2. 存储占用增加
3. 启动时间变长

**影响分析**:
- 影响范围: 长期使用用户
- 严重程度: 低（一年后才会显现）
- 发生概率: 高（只要用户持续使用）

**解决方案**:
1. 数据库分页加载
2. 只保留最近一年的详细数据
3. 旧数据归档到月统计

**需要在PRD中更新**:
- [ ] 非功能需求：数据量上限和归档策略

### 总结

**共发现 4 个问题**:
- 高优先级: 1 个（进程被杀）
- 中优先级: 2 个（时间作弊、忘记停止）
- 低优先级: 1 个（数据累积）

**需要在进入下一阶段前解决的问题**:
- 进程被杀导致的状态丢失（影响核心功能）
- 系统时间作弊（影响公平性）
```

## 注意事项

1. **至少3个挑战** - 符合SOP要求
2. **不同类型覆盖** - 边界、异常、体验都要有
3. **诚实面对问题** - 不要回避设计缺陷
4. **提出解决方案** - 每个问题都要有解决思路
5. **更新PRD** - 挑战发现的问题要同步到设计文档
